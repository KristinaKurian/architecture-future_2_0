# Task1 — «Будущее 2.0»: целевая архитектура и приоритизация

## Что подготовлено

1. **`target_architecture.puml`** — C4 Container-диаграмма целевой архитектуры через год.
2. **`problems_and_priorities.md`** — проблемы As-Is, затронутые бизнес-сценарии, приоритизация MoSCoW, ожидаемый эффект.

## Цели целевой архитектуры

- Убрать бизнес-логику предметных областей из общего DWH; домены самостоятельно управляют операционными системами и данными.
- Предоставить единый портал самообслуживания и контролируемый доступ к аналитическим витринам.
- Разделить клинический, ИИ, банковский и корпоративный контуры, сохранив сводные показатели бизнеса.
- Обеспечить масштабирование аналитики до сотен ТБ за счёт объектного хранения, раздельных вычислительных ресурсов и подготовки витрин.
- Дать новым организациям возможность присоединяться по опубликованным контрактам данных, без изменения логики центрального DWH.

## Ключевые бизнес-сценарии

| ID | Сценарий | Поддержка в целевой архитектуре |
|---|---|---|
| BS1 | Руководитель самостоятельно строит отчёт за доступные периоды/срезы | Портал → каталог → семантический слой → Gold-витрины; ограничения по ролям и строкам |
| BS2 | Руководство получает сводные финансовые и операционные KPI | Доменные data products из финтеха, клиник (только бизнес-агрегаты) и головного офиса → Lakehouse |
| BS3 | Финтех выпускает новые продукты независимо от клиник | Собственные API, бизнес-логика и транзакционные БД; обмен через версионированные контракты |
| BS4 | Клиника применяет ИИ для медицинских задач | Клиническое API ↔ Python AI в защищённом медицинском контуре; без выгрузки медданных в аналитику |
| BS5 | Подключение нового фарм-/электронного бизнеса | Новый домен публикует данные по контракту в ingestion, каталог и витрины; без правок логики общего DWH |
| BS6 | Высокая производительность отчётов на сотнях ТБ | Отдельные вычислительные контуры, партиционирование, SQL-движок, предагрегация и кеширование |
| BS7 | Соблюдение требований безопасности и устойчивости | IAM/SSO, RBAC/ABAC, изоляция, аудит, резервное копирование, контроль региона хранения и зон размещения |

## Принципиальные ограничения и допущения

**Медицинские карты, истории болезней и результаты исследований никогда не попадают в Lakehouse, BI и портал самообслуживания.** Разрешены только бизнес-показатели клиник, не содержащие медицинских сведений и сведений, раскрывающих информацию о конкретных пациентах. Запрет исполняется на уровне контрактов источника, выгрузки и проверок качества данных.

- Финтех хранит защищённые транзакционные и персональные данные внутри контролируемого контура. В центральную аналитику попадают только разрешённые наборы (по возможности агрегированные или минимизированные); права определяются классификацией и задачами сотрудника.
- Облако — целевая среда после проверки юридических ограничений, лицензий, требований регуляторов и допустимого расположения данных. Физическая инфраструктура банковского и медицинского контуров выбирается отдельно.
- Конкретные инструменты — примеры реализации, не обязательная закупочная спецификация: Kafka/CDC, Airflow+Spark, Iceberg, Trino, DataHub/OpenMetadata, Power BI.
- Старые DWH на SQL Server 2008, PowerBuilder и Apache Camel могут использоваться как временные интеграционные компоненты, но не становятся ядром целевой системы.
- Точные SLA, бюджеты, рост данных, требования к RPO/RTO и регуляторные границы не предоставлены и подлежат согласованию.

## Промежуточное состояние (через два месяца)

К этому сроку ожидаются **согласованные архитектурные решения**, а не полностью работающая платформа:

1. Зафиксированы границы четырёх доменов и владельцы источников/data products.
2. Утверждён запрет на использование медицинских данных в аналитике и подход к контролю потоков.
3. Описаны базовые контракты данных и политика доступа; определён набор первых KPI и пользователей портала.
4. Согласована схема миграции с SQL Server 2008/PowerBuilder/Camel и перечень доменных проектов.
5. Согласованы требования по размещению, отказоустойчивости и безопасности.

## Состояние через год

- Запущен портал самообслуживания с каталогом, конструктором отчётов, аудитом и разграничением доступа.
- Подключены минимум ключевые разрешённые показатели клиник, финтеха и головного офиса; ИИ использует клинические данные исключительно для медицинских задач.
- Новые источники могут подключаться через интерфейсы и контракты без переноса их бизнес-логики в Lakehouse.
- Устаревшие компоненты могут временно остаться внутри отдельных доменов по плану декомиссии.
