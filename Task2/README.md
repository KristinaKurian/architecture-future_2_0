# Task2 — Детализация доменов и моделирование потоков данных

## 1. Связь с заданием 1

В задании 1 уже выделены **четыре бизнес-домена**. Задание 2 **не вводит новые домены**: оно раскрывает их ответственность, собственные данные и взаимодействие для ключевых бизнес-сценариев.

1. **Клинические сервисы** — медицинские процессы и допустимые бизнес-показатели клиник.
2. **Медицинский ИИ** — выполнение медицинского анализа по запросу клиники.
3. **Банковские сервисы** — счета, платежи, кредиты и развитие финтех-продуктов.
4. **Корпоративное управление** — персонал, закупки, ресурсы и корпоративные финансы.

**Общая платформа данных** — техническая платформа хранения и аналитики, а не пятый бизнес-домен. **Legacy DWH/ESB** — временная техническая зависимость, а не домен. **Фармацевтическая и электронная системы** представлены как внешние участники/источники данных: они подключаются к уже существующему домену корпоративного управления. На данном этапе для них не вводятся отдельные домены.

Основа: [C4 из Task1](../Task1/target_architecture.puml), [описание архитектуры Task1](../Task1/README.md).

**Диаграмма:** [dfd_domain_flows.puml](dfd_domain_flows.puml) — DFD уровня 1, согласованная с C4 из Task1. На DFD `P*` — процессы, `D*` — хранилища данных, `E*` — внешние акторы/системы. DFD показывает **потоки данных**, а не сетевое развёртывание.

## 2. Границы и ответственность существующих доменов

| Бизнес-домен | Процессы / хранилища DFD | Собственная логика и данные | Разрешённые выходные потоки |
|---|---|---|---|
| **Клинические сервисы** | P1 — клиническая система, D1 — медицинская БД, P2 — публикатор бизнес-KPI | Карты пациентов, история болезни, обследования, записи на приём и внутренний учёт | P1 ↔ P3: защищённый медицинский API; P2 → P8: только агрегированные **немедицинские** показатели |
| **Медицинский ИИ** | P3 — сервисы медицинского ИИ | Диагностическая логика и обработка необходимого медицинского контекста; независимо версионируемые модели | P3 → P1: результат медицинского анализа; никаких медицинских данных в аналитическую платформу |
| **Банковские сервисы** | P4 — счета/платежи, D2 — БД операций, P5 — кредиты, D3 — БД кредитов, P6 — банковский публикатор | Транзакции, обслуживание продуктов, кредитные решения и соответствующие правила | P6 → P8: разрешённые банковские наборы, по возможности минимизированные и агрегированные |
| **Корпоративное управление** | P7 — ERP/HR/закупки/корпоративные финансы, D4 — БД корпоративных данных | Учёт ресурсов, затрат, закупок, персонала и взаимодействия с поставщиками | P7 → P8: разрешённые корпоративные KPI; E3/E4 → P7: данные партнёров по согласованным API |

## 3. Данные и каналы обмена

| Поток | Источник → получатель | Данные | Интерфейс и контроль |
|---|---|---|---|
| F01 | E1 → P1 ↔ D1 | Действия врача и медицинские документы | Клинический API, права на пациента, аудит |
| F02 | P1 → P3 → P1 | Необходимый медицинский контекст → результат анализа | Защищённый API, проверка цели обработки, минимизация |
| F03 | P1 → P2 → P8 | Загрузка клиник, посещаемость, расходы и выручка **без медсведений и идентифицирующих пациента данных** | API / Batch, утверждённые агрегаты, запрет малых раскрывающих групп |
| F04 | P4 ↔ D2, P5 ↔ D3, P4/P5 → P6 → P8 | Банковские операции внутри домена, затем разрешённые аналитические показатели | Доменные API, события / CDC / Batch, схема и классификация |
| F05 | E3/E4 → P7 ↔ D4 → P8 | Поставки фармацевтики, партии, оборудование, закупки, обслуживание и разрешённые показатели | Версионированные контракты через существующее корпоративное управление |
| F06 | E5 → P8 | Только разрешённые исторические данные старой системы | Временный миграционный адаптер и проверка состава |
| F07 | P8 → P9 → D5; P9 → P10 | Проверка контрактов и качества, техническое преобразование, витрины и lineage | Ingestion, обработка, каталог; без предметной бизнес-логики |
| F08 | E2 → P12 ↔ P10, P12 ↔ P11 ↔ D5 | Запрос отчёта, метаданные, разрешённые аналитические результаты | Портал / BI, семантический слой, доступ через P13 (IAM) |

Проверки на входе P8 выполняются **до сохранения данных в D5**. Псевдонимизация сама по себе не даёт разрешения на передачу медицинских данных. Медицинские карты, истории болезни, исследования, результаты диагностики и сведения, позволяющие их восстановить, в D5 не поступают.

## 4. Ключевые бизнес-сценарии

### S1. Клиника использует медицинский ИИ

1. Врач (E1) работает с клинической системой P1 и получает доступ к разрешённым данным D1.
2. P1 вызывает P3 через защищённый API и передаёт только необходимый для конкретной диагностической задачи контекст.
3. P3 возвращает результат в P1; клиническая система управляет дальнейшей записью результата в D1 и действиями врача.
4. Для управленческой аналитики отдельный процесс P2 формирует **немедицинские** агрегаты. Между D1/P3 и общей платформой P8/D5 **нет прямого потока медицинских данных**.

**Независимость:** модель ИИ может обновляться отдельно от клинического приложения при сохранении API-контракта. Общий DWH не участвует в диагностике.

### S2. Банк запускает новый финтех-продукт

1. Новый функционал реализуется **внутри домена «Банковские сервисы»**. Для этого используются или расширяются существующие сервисы счетов/платежей P4 и кредитов P5; при необходимости внутри этого же домена создаётся отдельный сервис, но **не новый домен**.
2. Счета, платежи и кредиты хранятся только в операционных БД D2/D3; правила кредитования и проведения платежей остаются внутри банковского домена.
3. P6 публикует разрешённый аналитический data product по версионированному контракту, а P8 принимает его без изменения центральной бизнес-логики.
4. Данные обрабатываются в P9 и доступны в D5 как подготовленные витрины с ограничением прав.

**Независимость:** новый банковский продукт не требует изменения клинических систем и добавления правил продукта в DWH.

### S3. Подключение фармацевтики и электроники

1. Фармацевтическая (E3) и электронная (E4) системы подключаются как **внешние источники**, не меняя список четырёх доменов.
2. E3 передаёт P7 сведения о поставках, партиях и закупках. E4 передаёт P7 сведения об оборудовании, поставках и сервисном обслуживании. Взаимодействия оформляются версионированными API/событиями с фиксированным владельцем данных.
3. P7 обрабатывает их в существующем контуре корпоративного учёта и сохраняет в D4. Только разрешённые закупочные, финансовые и операционные показатели поступают из P7 в P8.
4. Для включения нового показателя в отчётность согласуется контракт данных и трансформация витрины, **не изменяются бизнес-правила других доменов**. Телеметрия, содержащая медицинские или идентифицирующие пациентов сведения, не передаётся.

**Независимость:** подключение партнёра расширяет источники внутри корпоративного направления, а не создаёт отдельный бизнес-домен или новую логику общего DWH.

### S4. Руководитель формирует отчёт самостоятельно

1. P2, P6 и P7 публикуют разрешённые data products; P8 проверяет договорённый контракт, классификацию, схему и состав полей.
2. P9 выполняет проверки качества и **технические** преобразования и формирует витрины в D5; P10 регистрирует метаданные и lineage.
3. Руководитель (E2) выбирает доступные данные в портале/BI P12, используя каталог P10.
4. P12 отправляет запрос в P11, где применяются семантика KPI и правила доступа P13. P11 запрашивает разрешённую витрину D5 и возвращает результат P12.
5. Отчёт можно собирать из показателей разных направлений, но нельзя получить из аналитики медицинские карты, исследования или другие запрещённые данные.

**Независимость:** руководители создают новые отчёты без доработки бизнес-логики старого DWH или операционных систем доменов.

## 5. Правила обмена и управление данными

- **Владелец** каждого набора находится в одном из четырёх бизнес-доменов; только владелец изменяет свои операционные правила и БД.
- **Контракт данных** определяет имя, версию, схему, владельца, назначение, классификацию, разрешённые поля, частоту обновления, совместимость и контроль качества.
- **Операционные вызовы** выполняются по доменным API, а публикация для аналитики — через API, события, CDC либо Batch, если это разрешено по типу данных.
- **Безопасность**: IAM/SSO, RBAC/ABAC, аудит, шифрование в канале, минимизация до ingestion, отказ на запрещённые наборы, мониторинг качества и lineage.
- **Нет центральной предметной логики**: Lakehouse и семантический слой могут считать общие KPI и согласованные агрегаты, но не принимать кредитные решения, не диагностировать пациентов и не управлять поставками.
- **Legacy** мигрирует постепенно: E5 показан как временный источник через адаптер, а не как пятый домен.
