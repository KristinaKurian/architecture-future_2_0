# Task2 — Домены и потоки данных компании «Будущее 2.0»

## 1. Область задания

**Диаграммы:**
- [`dfd_domain_flows.puml`](dfd_domain_flows.puml) — DFD уровня 1: существующие и будущие бизнес-домены, их операционные хранилища, междоменные потоки и доступ к аналитике.

DFD описывают **данные и направления передачи**: прямоугольники `P*` — процессы, цилиндры `D*` — хранилища, `E*` — внешние участники/системы. Не являются диаграммами сетевого развёртывания или последовательности вызовов.

## 2. Границы доменов и ответственность

| Домен | Чем владеет / где бизнес-логика | Публикуемые междоменные данные | Что не публикуется в общую аналитику |
|---|---|---|---|
| **Клинические сервисы** | Работа клиники, запись пациентов, обследования; медицинская БД D1. Владелец — клиническое направление | P2: агрегированные **немедицинские** показатели посещаемости, загрузки, затрат и выручки | Медкарты, истории болезней, результаты исследований, пациентские события и идентификаторы, позволяющие восстановить медсведения |
| **Медицинский ИИ** | Выполнение диагностики P3, версии и конфигурации моделей D2; независимый цикл разработки ИИ. Владелец — ИИ-направление | Результат анализа **обратно в клиническую систему** по защищённому API | Медицинские данные, заключения и наборы для обучения не передаются в общий Lakehouse или BI |
| **Банковские сервисы** | Счета, платежи, кредиты P4, банковские данные D3, новые продукты P5. Владелец — банковский домен | P6: специально разрешённые банковские показатели и data products с минимизацией/агрегацией | Полные банковские записи, секреты, неразрешённые персональные и транзакционные данные |
| **Корпоративное управление** | Персонал, закупки, инвентаризация, корпоративные финансы P7/D4. Владелец — корпоративное направление | Показатели закупок, расходов, бюджета и запасов с контролем конфиденциальности | Неразрешённые персональные сведения сотрудников и закрытые корпоративные записи |

На DFD процесс **P4** агрегирует сервисы счетов, платежей и кредитов, которые подробнее представлены отдельными контейнерами на C4-диаграмме Task1. Это сознательное укрупнение уровня DFD, а не возвращение к банковскому монолиту.

**Общая платформа данных — платформенный контур, не бизнес-домен:** принимает только согласованные продукты данных, преобразует и агрегирует их, предоставляет витрины и самообслуживание. Она **не владеет бизнес-правилами** клиник, банковских продуктов, фармацевтики или электроники и не становится системой исполнения их операций.

## 3. Сценарии на DFD

### S1. Врач использует ИИ для диагностики (E1 → P1 ↔ P3)
1. Врач открывает медицинскую карту в P1; P1 читает D1.
2. P1 передаёт в P3 только необходимые для конкретной медицинской задачи данные по защищённому API с контролем полномочий и цели обработки.
3. P3 выполняет модель и возвращает диагностический результат в P1; медицинские результаты хранятся в клиническом контуре D1.
4. Независимое обновление P3 не требует менять клиническую БД или общий DWH при соблюдении контракта API.
5. **Отдельный поток:** P1 → P2 → P10 передаёт только безопасные агрегированные бизнес-KPI клиники. D1 → P10 / D7 **отсутствует**.

### S2. Банк подключает новый финтех-сервис (P5 ↔ P4, P5 → P6 → P10)
1. Новый продукт P5 интегрируется с P4 через версионированный банковский API, а не через SQL Server 2008.
2. Договоры, операции, платежи обрабатываются внутри банковского домена; D3 остаётся системой операционного учёта.
3. Новый продукт передаёт допустимые показатели P6; банковский публикатор формирует разрешённый data product.
4. Платформа P10 подключает продукт через контракт данных и добавляет показатель в витрину. **Новая бизнес-логика не внедряется в общий DWH.**

### S3. Подключение фармацевтики и производителя оборудования (P8/P9 → P10)
1. Каждая новая компания сохраняет собственное хранилище D5/D6 и правила предметной области.
2. Фармацевтика публикует показатели партий и поставок; электроника — технические KPI и простои. P10 проверяет схему, классификацию, владельца и правила экспорта.
3. При необходимости клиника получает поставки через P1 ↔ P8 и сервисные статусы устройств через P1 ↔ P9 — **напрямую через контрактные API**, без участия Lakehouse.
4. Новые данные могут войти в аналитические витрины, не меняя логику ранее подключённых доменов. Из телеметрии должны быть удалены данные пациентов.

### S4. Руководитель создаёт отчёт (P10 → D7 → P11 → E2)
1. Доменные публикаторы поставляют согласованные наборы с метаданными. На входе аналитики недопустимые данные отклоняются до записи.
2. Платформа проверяет качество, преобразует данные и готовит витрины D7.
3. Пользователь выбирает разрешённые показатели в портале P11; доступ к строкам/полям проверяется через семантический слой и IAM (показаны на детальной DFD).
4. Портал возвращает результат и сохраняет определение отчёта. Отчёт не содержит медицинских карт, историй или результатов исследований.

## 4. Принципы обмена, обеспечивающие независимость

| Правило | Почему важно для бизнеса |
|---|---|
| **Владение у источника**: только домен изменяет свою операционную БД и бизнес-правила | Новые функции клиник или банка не требуют правок в общем DWH |
| **Контракты с версиями**: схема, назначение, владелец, классификация, SLA обновления, правила совместимости | Партнёры подключаются предсказуемо; изменения обнаруживаются до поломки витрин |
| **API для операций, события/CDC/batch для аналитических публикаций** | Транзакционные процессы не зависят от долгих аналитических трансформаций |
| **Минимизация и контроль экспорта до ingestion** | Чувствительные данные не попадают в общую платформу; снижается риск утечки |
| **Семантика KPI в аналитике, бизнес-правила в доменах** | Можно собирать общую отчётность, не создавая новую централизованную операционную монолитную систему |
| **Независимое развёртывание** по версиям API/контрактов | Ускоряется time-to-market: изменение одного продукта не требует релиза всех доменов |

**Примечание о безопасности:** никакая форма псевдонимизации или агрегации не является автоматическим разрешением на передачу данных. Набор клиники допускается к платформе лишь после проверки, что он не содержит медицинских сведений и не позволяет их восстановить, в том числе через слишком узкие группы.
